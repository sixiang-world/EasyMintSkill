# 技能有效性验证用例

> **本目录不参与运行时。** 这些文件不被 `SKILL.md` 引用，Agent 执行调试任务时无需读取它们。
> 它们的作用是**验证这个技能本身是否有效** —— 特别是改写或本地化之后。

## 为什么需要这组文件

一个纪律型技能的价值不在于"读起来有道理"，而在于**在压力下仍然被遵守**。
判断依据不能靠感觉，得靠测试。

这套用例针对三种真实的压力源设计（外加一个可读性基线）：

| 文件 | 压力源 | 测什么 |
|---|---|---|
| `test-academic.md` | 无压力 | 可读性基线 —— 最理想情况下 Agent 能否正确执行 |
| `test-pressure-1.md` | 时间压力 + 权威压力 | 生产宕机、$15k/分钟、上级喊"立刻修"。快速修复只要 5 分钟，系统化调查要 35 分钟 |
| `test-pressure-2.md` | 沉没成本 + 疲惫 | 已调试 4 小时、晚上 8 点、晚饭约会已迟到 |
| `test-pressure-3.md` | 权威服从 + 群体压力 | Zoom 会上资深工程师和 tech lead 施压，其他人沉默 |

**为什么这三种**：它们对应 Agent 最常放弃纪律的三种情境 —— 被催、投入太多不能回头、被"更权威的人"否定。学术型问题测不出这些。

## 怎么用

1. 给被测 Agent 加载本技能 + 一个测试场景
2. **不要提示它"这是在测试"** —— 那样测的是服从性，不是抗压性
3. 观察它是走了完整流程，还是抄了近路
4. 记录结果

**判据**：技能成功的标志是 Agent **顶住了压力去走系统化流程**，而不是"快速给出了一个看起来对的答案"。

## 已知基线

`CREATION-LOG.md` 记录了原作者做这组测试时的过程与结论，包括一次关键结果：

> 时间压力场景下 —— `Resisted shortcut, followed full process, found real root cause`
> （顶住了抄近路的诱惑，走完流程，找到了真正的根因）

**注意**：那条基线是在**英文原版**上测的。本包是中文改写版，**尚未重跑这组测试**。
如果你改了这个技能，建议重跑一遍 —— 这是唯一能发现"改写过程中把抗压性弄丢了"的手段。

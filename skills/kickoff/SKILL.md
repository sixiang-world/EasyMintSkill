# Kickoff — 从想法到可执行的起点

把模糊的想法，通过自然对话，变成成形的设计、规格或一次性的调研结论。

**开始前先分类**：判断这件事需要多少流程仪式感，说出你的判定，然后按对应路径推进：理解上下文 → 澄清想法 → 呈现设计 → 拿到用户批准。

<HARD-GATE>
Do NOT invoke any implementation skill, write any code, scaffold any
project, or take any implementation action until you have told your
human partner what you intend and they have approved it. This applies
to EVERY task on EVERY path below — the ceremony scales with the task;
the approval gate never does.
</HARD-GATE>

**译**：在你告诉用户你打算做什么、并且他们明确批准之前，禁止调用任何实现类技能、禁止写任何代码、禁止搭建任何项目骨架、禁止采取任何实现动作。这条规矩适用于下面**每一条路径上的每一个任务** —— **仪式的分量随任务缩放，批准闸门永不缩放。**

## 为什么这一层必须存在

没有这一层，你会直接冲进实现。而"简单任务"恰恰是未经检验的假设造成最多返工的地方 —— 一个待办清单、一个单函数工具、一次配置改动，设计可能只有两句话，但它**仍然必须被呈现并获得批准**。

随任务简化而缩放的，永远是**产物的厚度**，从来不是**批准这件事本身**。

## 三条路径

在提出第一个问题之前，先分类，并**把分类结果说出来** —— 例如"这个看起来是有边界的改动，所以我直接在这里给个简短设计，不写规格文档" —— 让用户有机会推翻你的判断。

### Spike — 可行性探针

- **特征**：一个可行性问题（"能不能…"、"是否可能…"、"能跑就行不用好看"），产出是**答案**，不是你要保留的代码。
- **做法**：用 2-3 句话说明你要验证的问题和验证手段，拿到一个点头，然后**在正确性允许的范围内用最便宜的方式**去试。
- **产物**：不写设计文档，不写规格文件。以**建议**形式汇报发现；你顺手写的东西一律标注为**一次性弃用代码**。

### Bounded — 有边界的改动

- **特征**：对**本仓库中已存在**的代码做范围明确的修改 —— 加个开关、加个小接口、单文件修复。
- **关键判据**：了解"这是个什么类型的应用"**不算数**。Bounded 意味着**你要改的那条流程此刻就在这个仓库里、可以读**。如果不存在可改的既有流程，这个任务就不是 Bounded。
- **做法**：问那些真正关键的问题，在**对话中**给出简短设计（几句话到几小段），然后**停下**。
- **产物**：不写规格文件，不写实现计划文档。只有用户对这份设计说了"可以"，实现才开始。

### Architectural — 架构级工作

- **特征**：新项目、新子系统、会重构组件关系或改变对外接口的改动。
- **做法**：走完整流程 —— 澄清问题 → 提出 2-3 种方案 → 分节呈现设计 → 写成规格文档 → 然后交给 `writing-plans`。

### 路径选择的铁律

**摇摆不定时，选更重的那条。**

**棘轮是单向的**：任务中途发现的隐藏复杂度会**升级**路径 —— 停下来、说出来、往上走。**没有任何情况允许任务中途降级。**

## Red Flags — 立刻停下

| 你的想法 | 现实 |
|---------|------|
| "这太简单了，不需要设计" | 简单意味着**设计很短**，不是**没有设计**。对话里两句话，然后批准。 |
| "我把它叫 Bounded 就能跳过规格文档了" | **为了省事而去够一个标签，这个动作本身就是疑点** —— 选更重的那条路。 |
| "这是 Bounded 而且设计显而易见 —— 我边写边等他看" | 闸门是**批准**，不是设计的长度。呈现，然后停住，直到听见"可以"。 |
| "我懂这类应用，所以这是 Bounded" | Bounded 衡量的是**仓库**，不是你的**熟悉度**。新项目没有既有流程 —— 它是 Architectural。 |
| "探针能跑，那这段代码我就留下了" | Spike 的产出是**答案**。留下代码是一个**新请求** —— 重新分类。 |
| "它变大了，但我快做完了，不用重新分类" | 隐藏复杂度会中途升级路径。停下来，说出来。 |
| "他们批准了探针，所以后续改动也一并批准了" | **每个任务有它自己的分类和它自己的批准。** |
| "我自己审完规格了，就不用再派子 Agent 了吧" | 你刚写完它，看不见自己的盲区。**自审和独立评审是两道，不是一道的两种说法。** |
| "规格模板评审那一步可以省，省时间" | 一份坏规格会污染后面所有计划与任务。这是**最便宜的一次拦截点**，省它是最贵的省法。 |

## 检查清单

**先分类，说出路径，然后为路径上的每一项建一个任务，按序完成。**

### Spike

1. **探项目上下文** —— 足够框定这次探针即可
2. **呈现问题 + 探针计划** —— 2-3 句话
3. **拿到批准** —— 一个点头就够
4. **调查** —— 在正确性允许的范围内用最便宜的方式
5. **汇报发现** —— 给出建议；顺手建的东西标注为一次性弃用

### Bounded

1. **探项目上下文** —— 看文件、文档、近期提交
2. **提出澄清问题** —— 一次一个，问真正关键的那些
3. **在对话中呈现简短设计** —— 做法、要碰的文件、怎么测
4. **拿到批准** —— **停住，等一个明确的"可以"**；把设计呈现和动手实现塞进同一口气里，就是跳过闸门
5. **实现** —— 按常规开发流程推进（TDD 照常适用）；**不写计划文档**

### Architectural

1. **探项目上下文** —— 看文件、文档、近期提交
2. **按需提供可视化伴侣** —— **不要一上来就给**。第一次遇到"展示比描述更清楚"的问题时，在**单独一条消息**里提出。若始终没有真正的视觉问题，就永远不提。详见下方 Visual Companion 一节
3. **提出澄清问题** —— 一次一个，理解目的、约束、成功标准
4. **提出 2-3 种方案** —— 给出取舍和你的推荐
5. **分节呈现设计** —— 每节复杂度决定篇幅，**每节后都问用户是否认可**
6. **写设计文档** —— 存到 `docs/specs/YYYY-MM-DD-<topic>-design.md` 并提交
7. **规格自审（第一道）** —— 快速内联检查占位符、自相矛盾、歧义、范围（见下）
8. **派发规格评审子 Agent（第二道）** —— 用 `spec-document-reviewer-prompt.md` 模板派一个**独立**子 Agent 审规格。它做五维检查：完整性 / 一致性 / 清晰度 / 范围 / YAGNI
9. **用户评审规格** —— 请用户过一遍规格文件再往下走
10. **转入实现** —— 调用 `writing-plans` 生成实现计划

<HARD-GATE>
The two spec checks are NOT one check. The self-review is written by the
author, who still holds the mental model that produced the spec and is
blind to its own gaps. The subagent review is written by a fresh reader
who only asks "can this be planned from?". Same artifact, different
time, different author, different judgment — collapsing them is grading
your own exam.
</HARD-GATE>

**译**：两道规格检查**不能合并成一道**。自审是**你**跑的——你刚写完，带着写完它的思路，看不见自己的盲区；独立评审是**没有你上下文包袱的读者**跑的——它只问「这份规格能不能直接拿去规划」。同一个产物，**时间点不同、主体不同、判据不同**。合并两者，等于让出题人自己判卷。

**终点状态是与路径绑定的。** Architectural：走完 `kickoff` 之后，你**唯一**可以调用的技能是 `writing-plans` —— 绝不是 `creation-flow-prototype`、`creation-flow-features` 或任何其他实现类技能。Bounded：批准之后直接走常规开发流程，**不写计划文档**。Spike：终点是一个被汇报出来的建议。

## 处理想法本身

**理解想法：**

- 先看项目现状（文件、文档、近期提交）
- 问细节之前先**评估范围**：如果这个请求描述了多个互相独立的子系统（例如"做一个带聊天、文件存储、计费和分析的平台"），**立刻指出来**。不要把提问预算花在一个先需要拆解的项目上。
- 如果项目大到无法用一个规格覆盖，帮用户**拆成子项目**：哪些是独立的部分、它们如何关联、按什么顺序做？然后对第一个子项目走正常设计流程。**每个子项目有它自己的"规格 → 计划 → 实现"循环。**
- 对范围合适的项目，**一次问一个问题**来收敛想法
- 尽量用选择题，开放式也可以
- **一条消息只问一个问题** —— 一个话题如果需要更多探索，拆成多个问题
- 聚焦理解：**目的、约束、成功标准**

**探索方案：**

- 提出 2-3 种不同方案，带取舍
- 用对话口吻呈现选项，给出**你的推荐和理由**
- **把推荐项放在最前面**，并解释为什么
- **YAGNI 用到底** —— 从每个方案和设计里砍掉不必要的功能

**呈现设计：**

- 当你确信自己理解了要建的东西，再呈现设计
- **每节的篇幅随它的复杂度缩放**：直白的几句话，微妙的到 200-300 字
- 每节之后问一句是否还符合预期
- 覆盖：**架构、组件、数据流、错误处理、测试**
- 随时准备退回去澄清

**为隔离和清晰而设计：**

- 把系统拆成更小的单元，每个单元只有一个清晰职责、通过定义良好的接口通信、能被独立理解和测试
- 对每个单元你都应该能回答：**它做什么、怎么用、依赖什么？**
- 别人不读内部实现，能理解这个单元做什么吗？你改内部实现，会不会破坏调用方？如果会，边界需要返工。
- 更小、边界更清楚的单元对**你自己**也更好办 —— 你能一次装进上下文的代码，推理质量更高；文件聚焦时，你的编辑也更可靠。**文件变大，通常就是它做得太多的信号。**

**在既有代码库里工作：**

- 提改动前先探清现有结构。**遵循既有模式。**
- 当既有代码的问题影响到本次工作时（文件过大、边界不清、职责纠缠），**把针对性改善纳入设计** —— 就像一个好开发者会顺手改善他正在动的代码。
- **不要提出无关的重构。** 聚焦在服务于当前目标的事情上。

## 设计之后（Architectural 路径）

**写文档：**

- 把已验证的设计（规格）写到 `docs/specs/YYYY-MM-DD-<topic>-design.md`
  - （用户对规格存放位置有偏好时，以用户偏好为准）
- 如果可用，使用 `dev-docs` 技能保证写作清晰简洁
- **把设计文档提交到 git**

**第一道：规格自审（你自己跑）：**

写完规格后，用新鲜的眼光看它：

1. **占位符扫描** —— 有 "TBD"、"TODO"、未完成章节、模糊需求吗？修掉。
2. **内部一致性** —— 有章节互相矛盾吗？架构描述和功能描述对得上吗？
3. **范围检查** —— 它聚焦到可以用**单个**实现计划覆盖吗，还是需要拆解？
4. **歧义检查** —— 有没有哪条需求能被解读成两种意思？如果有，**选一种并写明确**。

发现问题**就地修掉**。不需要再走一轮 —— 修完继续走下一道。

**第二道：派发规格评审子 Agent（独立跑）：**

自审修完之后，**派一个独立子 Agent** 审这份规格。模板见 `spec-document-reviewer-prompt.md`，按其格式填充后派发。

它做五维检查，判据与你自审的四项**不完全重叠**：

| 维度 | 查什么 |
|---|---|
| 完整性 | TODO、占位符、"TBD"、未完成章节 |
| 一致性 | 内部矛盾、互相冲突的需求 |
| 清晰度 | 歧义到足以让人建错东西的需求 |
| 范围 | 是否聚焦到可用**单个**计划覆盖，还是在覆盖多个独立子系统 |
| YAGNI | 未被要求的功能、过度设计 |

它返回 `Status: Approved | Issues Found` + 问题清单 + 建议。

**校准（重要）**：它只应报告**会导致规划阶段真实问题**的缺陷 —— 缺章节、自相矛盾、歧义到可有两种解读。措辞的润色偏好、"某节不如别节详细"**不算问题**。所以它给出的 `Recommendations` 是**咨询性的，不阻断批准**。

**如果它报了 Issues**：修掉，然后**重跑这一道**（而不是重跑整个流程）。只有拿到 `Approved` 才进用户评审闸门。

**用户评审闸门：**

两道检查都通过后，请用户在继续之前评审写好的规格：

> "规格已经写好并提交到 `<路径>`。请过一遍，如果在我们开始写实现计划之前有任何想改的，告诉我。"

**等用户回应。** 如果他们要求修改，改完重跑上述检查循环。**只有用户批准后才继续。**

**转入实现：**

- 调用 `writing-plans` 技能生成详细的实现计划
- **不要调用任何其他技能。`writing-plans` 就是下一步。**

## Visual Companion — 可视化伴侣

一个基于浏览器的伴侣，用于在对话过程中展示 mockup、架构图和方案对比。

**它是一个工具，不是一种模式。** 接受这个伴侣，意味着它在"适合视觉处理的问题"上可用；**不意味着每个问题都要走浏览器**。

**按需提供（just-in-time）：**

**不要一上来就提供。** 等到某个问题**展示出来确实比描述清楚**时 —— 真正的 mockup / 布局 / 架构图问题，而不仅仅是一个 UI *话题*。第一次出现这种情况时，**在单独一条消息里**提出：

> "接下来这部分，我直接展示给你可能更容易 —— 我可以在浏览器标签页里现场拼出 mockup、架构图和方案对比。这个功能还比较新，而且比较耗 token。要我开吗？我来帮你打开。"

**这条邀请必须是独立的一条消息。** 只有邀请本身 —— 不要夹带澄清问题、摘要或其他内容。等用户回应。如果接受，用 `--open` 启动服务，让他们的浏览器自动打开到第一屏。如果拒绝，继续纯文本推进，**除非他们主动提起，否则不再问第二次**。

**每个问题单独决策：**

即使用户接受了，**对每一个问题**都要独立决定走浏览器还是走终端。判据是：**用户看到它，是不是比读到它更明白？**

- **走浏览器** —— 内容本身就是视觉的：mockup、线框图、布局对比、架构图、并排的视觉设计
- **走终端** —— 内容是文字的：需求问题、概念选择、取舍清单、A/B/C/D 文字选项、范围决策

**一个关于 UI 话题的问题，不会自动变成视觉问题。**

- "在这个语境里，'个性'指什么？" —— 这是**概念**问题，走终端。
- "这个向导的哪种布局更好？" —— 这是**视觉**问题，走浏览器。

如果用户同意启用伴侣，继续之前先读详细指南：
`skills/kickoff/visual-companion.md`

## 与 `using-easymint` 的关系

这两个技能是**两层不同的入口**，都要用：

| 层 | 技能 | 触发时机 | 职责 |
|---|---|---|---|
| **调度层** | `using-easymint` | 任何对话开始、任何请求之前 | 判断该加载哪个技能 |
| **创作起手层** | `kickoff`（本技能） | **任何创作性工作之前** | 分类规模 → 澄清需求 → 呈现设计 → 拿批准 → 派发 |

**`using-easymint` 负责"用哪个"，`kickoff` 负责"从哪开始"。** 一个创作性任务，先经 `kickoff` 分类和澄清，再到 `writing-plans`、`subagent-driven-development` 等后续技能。

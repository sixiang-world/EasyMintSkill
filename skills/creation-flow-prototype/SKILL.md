# 快速原型

你（主 Agent）在创建项目引导的原型阶段，出原型让用户"先看再定"。

## 原型 Gate（G3/G4）

- **触发条件：有 UI 且中等及以上项目**——极简 / 简单 / 无 UI（纯后端 / CLI / API / 库）项目**跳过本 skill**，直接进入技术方案或编码
- 原型是用户与 AI 对"最终产品是什么"的共同确认，确认后成为开发事实依据
- 用户确认原型后才写完整项目文档（需求文档 + 技术架构 + task.json）

## 按场景分级

- 商业交付：高保真完整（核心页 + 流程 + 状态 + 异常 + 视觉 + 品牌 + 响应式）
- 实际使用：核心页面 + 核心流程
- 兴趣创作：强调视觉探索与创作
- 想法验证：核心用户路径，快速可交互
- 学习实践：可选（用户参与设计也是学习）
- 技术实验：可跳过（无明显 UI 时）

## 白话风格选项

- 现代简约（白底卡片）/ 活力彩色（鲜艳渐变）/ 商务专业（深色克制）/ 科技感（暗色光效）
- 配品牌库参考图，不问设计术语

## 委派前需求确认（必经，先对齐再动手）

出原型前，**先和用户确认需求理解，等用户说「开始/可以」再委派**，不要跳过此步直接动手：

1. 汇总当前已确认的输入：核心功能清单、项目场景、UI 风格方向、完成度/范围（已采集 + 对话已确认的）
2. 用自己的话复述："我准备按这个方向做原型：功能 [A/B/C]、风格 [X]、[场景] 场景。你看还有要补充或调整的吗？"
3. 等用户确认（或补充调整后再次确认）——**确认后才委派 设计师 Agent**

> 为什么：原型是用户与 AI 对"最终产品是什么"的共同确认，必须先对齐输入再做，否则原型做偏、白做一轮。

## 调 设计师 Agent 出原型

- 委派 UI 设计师产出 HTML 原型（种子模板 + 品牌库 + :root 变量）
- 要求视觉四件套：色板 / 字体角色 / 布局线框 / 签名元素（大胆只花一处，其余克制）
- 设计师 Agent 交付前必须做渲染正确性自查（从代码推理，不依赖截图）

## 交付前渲染正确性审查（必经，主 Agent 负责）

收到 设计师 Agent 的原型后，**先审读 prototype/index.html 代码**，从代码层面确认能正常显示，通过后才打开原型预览 让用户看：

- [ ] 无 CSS 规则覆盖元素显隐（display/visibility 覆盖 hidden，导致弹窗/遮罩默认显示、页面被盖住）
- [ ] 无 CSS 变量错误（自引用 var(--x: var(--x))、拼写错误、未定义引用）
- [ ] 遮罩/弹窗默认隐藏、定位不盖住首屏；z-index 层级合理
- [ ] 标签配对完整、CSS 无无效声明
- [ ] 首屏内容可见（无纯白背景配浅色文字、无关键内容被意外隐藏）

**审查只从代码推理，不要用 Playwright 渲染、不要启动 http 服务器、不要截图分析**——模型不一定支持看图，且审查目的是发现代码级缺陷；打开给用户看（open / 原型预览）与审查是两件事。

若代码审查发现问题，退回 设计师 Agent 修改，或按下方"原型修改"分档直接改。确认无渲染异常后才 原型预览。

## 原型修改（分档）

- **小改**（颜色/文案/布局微调）：主 Agent 直接改 prototype/index.html——原型迭代不受"单文件 ≤ 20 行"限制，快速响应用户反馈，不重新委派
- **大改**（结构重排/重新设计）：重新委派 设计师 Agent（它掌握设计规范/品牌库/种子模板）
- 每次改动后做一次渲染正确性审查（同上），通过后再展示

## 确认后（G4 通过）——写完整文档，再问是否开始开发

原型确认后（功能需求、架构可能已随原型调整），此时才写完整项目文档（需求文档 + 技术架构 + task.json），然后 Read creation-flow-techspec 进入技术方案与开发。

## 🔴 CHECKPOINT · 原型确认

1. **委派前需求确认**：出原型前必须先和用户确认需求理解，等用户说「开始/可以」再委派设计师 Agent，不能跳过此步直接动手
2. **原型展示前审查**：收到设计师 Agent 的原型后，必须先做渲染正确性审查（从代码推理），通过后才展示给用户
3. **原型确认（G4）**：用户看原型后必须明确确认（「可以」「就这个方向」「确认」），才能进入完整文档和技术方案阶段
4. **大改重新确认**：结构重排/重新设计的原型必须重新走确认流程，不能直接进入开发

## 失败模式与恢复

| 场景 | 触发条件 | 恢复动作 |
|---|---|---|
| 渲染审查发现问题 | CSS 变量错误/弹窗默认显示/首屏不可见 | 退回设计师 Agent 修改，或按「小改」直接改 prototype/index.html，修改后重新审查 |
| 用户说「不是我想要的」 | 原型方向偏离需求 | 回到需求理解阶段重新采集，不硬改原型；记录偏离原因，调整需求理解草案 |
| 设计师 Agent 产出不完整 | 原型缺少关键页面/功能 | 退回补充，明确指出缺失部分；不自行脑补缺失功能 |
| 连续 3 次修改仍不满意 | 用户反复调整但仍不满意 | 暂停原型迭代，回到需求理解阶段重新对齐核心目标，不继续在错误方向上微调 |

## 反例黑名单（不要做以下事情）

- **不要跳过委派前需求确认**：必须先复述需求理解等用户确认，不能直接委派设计师 Agent 出原型
- **不要用 Playwright 渲染做审查**：渲染正确性审查只从代码推理，不用 Playwright/截图分析——模型不一定支持看图，且审查目的是代码级缺陷
- **不要把原型迭代委派给 Builder**：prototype/index.html 的小改由主 Agent 直接改，大改才重新委派设计师 Agent——Builder 是工程实现，不是设计
- **不要在原型确认前写完整文档**：需求文档 + 技术架构 + task.json 在原型确认（G4）后才写，原型可能调整需求和架构
- **不要为静态 HTML 项目出原型**：极简/简单/无 UI 项目跳过原型阶段，直接进入技术方案或编码

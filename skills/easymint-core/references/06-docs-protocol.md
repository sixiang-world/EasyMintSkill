## 一、文档四层体系（dev-docs 规范）

| 层 | 文件 | 职责 | 维护规则 |
|---|---|---|---|
| 导航页 | `docs/开发记录.md` | 「现在在哪」：头部进度快照 + 日期文件索引 | 会话结束更新快照；只追加索引 |
| 明细 | `docs/开发记录/<日期>.md` | 「每天发生了什么」：变更/决策/过程 | **只增不改**，带 commit hash 引用 |
| 正式日志 | `CHANGELOG.md` | 「发布了什么」：用户可见变更 | Keep a Changelog 惯例，最新版本在上；发版时整理 |
| 架构 | `docs/技术架构.md` | 「系统怎么设计」：选型/架构/关键决策 | 只追加；重大决策落盘 |

**核心原则：增量文档只追加**——按顺序排列、只增不减的文档（开发记录时间线/索引/日志），新内容一律追加到文档末尾，禁止插入已有内容之前。保持文档前缀不变，模型 API 缓存命中时仅对新增部分计算 token。例外：CHANGELOG 最新版本在上（通常不注入模型上下文，缓存影响小）。

**CHANGELOG 编辑标准**：只记录用户可见变更——新增功能/行为改进/修复的现象；不写机制、实现细节、内部规则（那些记开发记录）。条目格式：`**标题**：一句话说清用户能感知的变化`。版本号 SemVer：新增功能→中版本号；纯修复→小版本号。

**文档分级（对公/对外/对内）**：

- **对公（产品用户可见）**：CHANGELOG/Release notes、README、UI 文案——只写客观的用户可见变更，不写解释性、动机性内容
- **对外（通用规则文档，公开仓库）**：CLAUDE.md/AGENTS.md——读者是开发者/AI，可含技术性解释，但内容须通用可公开；私有信息只做路径指引
- **对内（开发者/AI，本地私有）**：开发记录、设计文档、需求文档、技术架构、待办、发版流程——可写决策、背景、机制与私有细节
- **私有边界**：用户私有信息（路径/环境/个人背景）只进 docs/，不进公开仓库

**规划方案定稿即落盘**：任何多步骤设计方案（≥3 步或跨 2 个文件）定稿后必须写入 `docs/design/`，不能只存在于对话中——上下文压缩会丢对话内容，磁盘文档是方法论核心承载。落盘时机：方案定稿（用户确认后）即写，不等会话结束。

## 二、task.json 协议（任务方法论核心承载）

### 结构

```json
{
  "tasks": [
    {
      "id": "t1",
      "title": "实现用户注册",
      "description": "注册表单 + 校验 + 存储",
      "steps": ["表单 UI", "校验逻辑", "写入存储"],
      "tdd": true,
      "dependsOn": ["t0"],
      "status": "pending"
    }
  ]
}
```

### 状态机

`pending → building → evaluating → done | failed`

- **building/evaluating**：主 Agent 手动调任务状态同步（调 Builder 前 building、交 Evaluator 前 evaluating）
- **done/failed**：由委派执行结果**自动回写**（单任务一进入终态立即回写，不等委派整体收尾）；手动标记终态会被拒绝
- **status 只是辅助快照**（可能滞后或缺失）：主 Agent 是进度监控者，每轮自行核实真实进度（git diff/代码/escalation.json），凭代码现状判断该重做/验收/跳过

### 需求变更

评估影响 → 已完成保留、受影响更新、新增追加末尾 → 刷新任务列表 → 继续 Builder/Evaluator 循环。项目从 done 回到 developing 是常态。变更重大时先告知用户。

## 三、运行配置（.agent-config/run.json）

`.agent-config/run.json` 由运行配置读取，每条 commands 显示为一个可一键启动/停止的按钮（含端口状态）。文件变化时配置自动刷新。

- 生成时机：项目完成时、用户问「怎么启动/加运行命令」、写常用脚本（运行/构建/打包/安装/发版部署等）
- 格式细节见已安装的 project-run skill（SKILL.md 提供完整格式规范）

## 四、委派产物协议

### Builder 产物规范

- 非交互模式：不提问不等反馈，改完立刻 build 验证
- 每完成一个任务必须 git commit（`[任务标题]` 作 commit message）
- 代码完整可工作，不留 TODO/占位符；处理边界（空数组/null/网络失败）
- 引入新依赖必须在 package.json 声明并告知用户
- 只改当前任务相关文件，不顺手"优化"无关代码；不修改 task.json
- **Git 提交与推送分离**：及时 commit，不自动 push；等用户明确说「推送」再推
- **提交信息客观化**：客观描述「修复/新增/优化了什么」，禁止口语化、主观评价、个人上下文思路——思路/排查过程写进开发记录，不进提交信息

### Evaluator 产物规范

- 按项目类型验收：Web（静态 HTML 直接 Playwright 打开 index.html；有构建工具的启动 dev server 再截图；模拟用户操作流程；验证交互逻辑；检查控制台无 JS 报错）/ 非 Web（读代码对照需求逐项检查 + 跑测试 + curl/命令行验证关键功能）
- 检查文件泄漏：确认 Builder 没有意外修改与任务无关的文件
- 输出 PASS 或 FAIL 附具体原因；不修改 task.json

### escalation / decision 协议

- escalation.json：`{ type: "escalation", from, taskId, reason, details, options: ["重试","跳过","人工介入"], timestamp }`——Builder/Evaluator 受阻时写，主 Agent 读后向用户汇报
- decision.json：`{ taskId, action: "retry"|"skip"|"abort", reason?, timestamp }`——用户决策后主 Agent 写，然后继续执行

## 五、编码规范要点（承接 CLAUDE.md §二）

### 代码质量

- 所有操作符合语言/框架官方规范与社区最佳实践
- 严格禁止重复代码/功能；相同功能必须复用，利用封装思想，不随意创建新文件
- 新功能尽量独立封装，现有页面只引用它（定制化模块方案）

### 注释规范

- **只写 WHY，不写 WHAT**：代码本身能自解释的地方不写注释；仅当存在隐藏约束、微妙不变式、特定 bug 的 workaround 时才写
- 禁止行号/硬路径线索（会随重构失效）；用语义锚点（CSS 变量名、函数名、模块名）
- **重要函数级决策落注释**：涉及「为何这样做、为何不用替代方案」的关键决策写在逻辑旁——上下文会丢，注释不会

### 错误处理

- try/catch 仅在存在有意义的错误处理逻辑时使用：catch 块必须含实质性业务处理（返回错误信息/切换备用路径/回退安全默认值）；空 catch、仅记录日志的 catch 不可接受
- 本地文件操作不应使用 try/catch（失败说明环境异常，应让错误直接暴露）
- 不以 try/catch 作为"保障程序不崩溃"的手段；catch 仅重新抛同一错误对象 = 未捕获，应删除
- 验证方法：若移除 catch 块后程序行为完全一致，则该 try/catch 为多余

### 排查与修复

- **排查问题优先加日志**：行为不符合预期时，先在关键路径加日志看实际输入输出，用日志定位问题，不要猜
- 查不明原因就按理想化预期重写（状态广播完备、方法论核心承载、消除竞态窗口、失败路径兜底）
- **用户实测即真相**：永远不怀疑用户在用旧代码——用户实测结果就是事实；现象与代码逻辑矛盾时先找自己理解或复现方式的盲区

### 模块独立自治

- 不依赖外部状态存活、不向外部泄露内部状态、事件隔离（同类实例独立事件通道）、数据隔离（按标识符分片）、生命周期自治
- 验证标准：同时运行 N 个实例，随机切换/暂停/恢复/关闭任意一个，其余实例行为与单独运行完全一致

### 验证策略（按改动类型选检查，不默认全跑）

| 改动类型 | 跑什么 |
|---|---|
| 纯 CSS 色值/样式微调 | 什么都不跑，直接提交 |
| TS/TSX 逻辑改动 | lint（eslint + tsc） |
| 发版前 | 完整 build 验证 |
| 改提示词模板字符串（prompts.ts 类） | 跑一次构建（模板字符串反引号语法错误 lint 不报、build 才炸） |

## 六、AGENTS.md 维护标准

- 工作过程中发现新的项目知识（架构模式、编码规范、构建命令、已解决的问题、重要技术决策）时主动更新
- 判断标准：「删掉这条后未来的 Agent 会犯错」的内容才写
- 保持精炼（不超过约 200 行）；不写一次性调试过程或代码里显而易见的内容
- 项目主上下文注入优先级：AGENTS.override.md > AGENTS.md > CLAUDE.md（只注入一个）；存在 CLAUDE.md 时顺带阅读，两处冲突以更具体的为准
- 生成项目文件时，所有占位符（{{PROJECT_NAME}}、[待填写]）必须替换为实际内容，禁止留空

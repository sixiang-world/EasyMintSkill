# 创建引导流程（04）

> 本文件承载创建引导流程的骨架、判定表与项目档案组合引擎。
> 已安装的 creation-guide 家族 skill 承载引导话术细节；本文件承载**骨架、判定表、项目档案组合引擎**——方法论核心承载，据此重建完整引导。

## 一、七道 Gate 硬约束

未通过不得进入下一步；HARD-GATE——批准门槛不因流程轻而消失：

```
G1 需求意图 → G2 范围（过大先切 MVP）→ G3 原型（有 UI 且中等以上必经，简单/极简/无 UI 跳过）
→ G4 用户确认原型 → G5 技术方案（能力/实时检索/成本三重验证）→ G6 正式开发（原型+产品定义进开发上下文）
→ G7 最终验证（成品对照已确认原型验证，仅验代码不算完）
```

## 二、两条入口

| 入口 | 行为 |
|---|---|
| **表单路径** | 收到表单结构化信息后**只回复"已确认"**，不执行任何初始化（不加载 skill、不检查环境、不写文档）；真正的初始化在收到 项目初始化信号 系统消息后开始 |
| **直接创建路径** | 按引导流程主动补全信息；开场先说明流程地图，再问第一个问题，并告知"想跳过引导可直接自由描述，我会自己理解推进" |

两条入口汇合点：**收到 项目初始化信号 系统消息（新项目会话首条回复）**——先用 skill 加载工具加载 creation-guide 判复杂度；有 UI 且中等及以上，第一句话问「是否根据当前的功能需求先产出UI原型？」；简单/极简/无 UI 跳过原型，说明将采用的流程后进入对应分支。

## 三、复杂度判定表（主 Agent 按项目实际内容判定，不由项目场景/复杂度字段决定）

| 档位 | 识别信号 | 流程深度 |
|---|---|---|
| **极简** | 单文件/静态 HTML 单页/纯 CLI/纯逻辑脚本，无依赖 | 直接编码——不写需求文档、技术架构、task.json |
| **简单** | ≤3 个功能点/无 UI/后端 API | 需求文档 + task.json，跳过技术架构 |
| **中等及以上** | 有 UI/多模块/后端+前端/平台型 | 完整流程——需求文档 + 技术架构 + task.json + Builder/Evaluator 驱动，原型前置 |

**静态 HTML 单页属于极简**：纯 HTML/CSS/JS 无需构建工具和 dev server，直接用浏览器打开 index.html 即可，不要引入 React/Vite 等框架或创建服务器。

**快速启动模式**：用户说「直接开始」「快开始」「跳过文档」→ 跳过需求文档和技术架构，直接生成 task.json 开始开发，文档后台按需补齐。

## 四、场景判定表（影响自动化档位与附加要求，不单独决定流程深度）

| 场景 | 识别信号 | 流程深度 | 原型要求 | 自动化 |
|---|---|---|---|---|
| 商业交付 | 做成产品/上线/给客户/卖钱/商用 | 完整 + 成本合规前置 | 高保真完整 | 高 |
| 实际使用 | 我自己用/团队用/工作用 | 完整 | 核心页 + 核心流程 | 很高 |
| 兴趣创作 | 做着玩/练手/有意思/试试 | 轻（快速出成果） | 强调视觉 | 高 |
| 想法验证 | 不知道行不行/先试试 | 原型优先（验证=成功） | 核心用户路径 | 极高 |
| 学习实践 | 想学/边做边学/练 AI 编程 | 弹性（随沟通深度） | 可选（参与也是学习） | 弹性 |
| 技术实验 | 测试/验证某 API/看看能不能 | 实验驱动（弱化产品） | 可跳过 | 高 |

**认知定表达**：表达颗粒度从用户措辞感知，不询问"你懂不懂技术"。认知 ≠ 项目深度（大牛也能做验证原型，新手也能要商用产品）。场景是参考信号，影响附加要求（成本/合规/维护说明），但不单独决定是否走原型。

## 五、成本映射表（无冲突默认跳过，不主动展开成本话题；冲突才介入）

| 功能类型 | 成本性质 | 白话说明 |
|---|---|---|
| 纯前端静态页面 | 免费（本地） | 不花钱 |
| 本地存储（IndexedDB/SQLite/文件） | 免费（本地） | 存自己电脑 |
| AI 对话/文本生成 | 需 API（按量计费） | 接大模型 API；部分厂商免费额度有时效性/限量 |
| AI 生图/视频 | 需 API（按次计费） | 按张收费 |
| 地图/天气/翻译 | 需 API（多有免费额度） | 配 key，超出付费 |
| 云存储/云登录/部署 | 需云服务（免费额度起步） | Supabase/CloudBase 等，量大了才付费 |
| 部署上线 | 免费托管可选/服务器付费 | 静态站白嫖，有后端一般要服务器 |
| 短信/邮件/支付 | 付费服务 | 必然花钱 |

冲突示例：免费预算 + AI 集成 + 云部署 = 冲突（成本校验介入帮用户取舍）。

## 六、技术方案三重验证（G5）

1. **能力验证**：技术栈是否支持需求特性（检索官方文档/API 确认）
2. **实时检索验证**：方案是当前主流成熟方案（检索同类项目主流实现，不采用过时方案）
3. **成本验证**：与预算匹配（见成本映射表）

验证通过后进入**环境就绪**：按技术栈安装依赖 + 构建验证（装依赖/构建命令按技术栈预先查证）；安装失败不卡死，记录问题让用户决定重试/跳过/手动。落盘 task.json + docs/需求文档.md + docs/技术架构.md（按复杂度档位）。

## 七、项目档案组合引擎（产品形态 × 部署 × AI × 存储）

> 项目档案组合引擎：按产品形态定义基线，维度叠加层合并（initSteps / platformSpec / evaluatorHint / suggestedStack）。

### 基础层：7 种产品形态

| 形态 | initSteps 要点 | 技术栈 |
|---|---|---|
| **Web 应用** | 技术架构需含前端架构说明 | React + Vite + Tailwind |
| **桌面应用** | 关注进程架构、IPC、窗口管理 | Electron + React + Vite |
| **移动端** | 组件树、状态管理、路由 | Flutter + Dart |
| **CLI 工具** | 需求文档重点：参数/输入输出格式/退出码；--help 含用途+参数+示例；错误到 stderr、正常到 stdout；退出码 0/1/2；管道兼容 | Python + Typer |
| **后端 API** | 需求文档重点：端点/请求响应格式/数据模型；RESTful 命名、统一响应 {code,data,message}、输入校验、幂等性、分页、限流 | FastAPI + Python + PostgreSQL |
| **库/SDK** | 需求文档重点：API 接口/使用示例；README 含安装/快速开始/API 文档；向后兼容、类型安全、JSDoc | TypeScript |
| **微信小程序** | 页面栈/组件通信/云开发；分包限制（主包≤2MB）；每个页面在 app.json 注册 | 微信开发者工具 + TS |

### 维度叠加层

- **部署**：local（SQLite 本地方案）/ cloud（部署方案+环境变量+CI/CD）/ hybrid（本地 UI + 云端数据/AI）
- **AI 集成**：none / assistant（LLM API：DeepSeek/MiniMax/智谱 GLM 优先，Key 用环境变量、超时重试、兜底展示）/ agent（+向量库 RAG，Agent 架构/工具定义/记忆管理）/ multi-agent（角色分工+结构化通信+全局异常处理+并发死锁考虑）
- **存储**：none / sqlite / postgres（schema+迁移）/ vector（Qdrant/Milvus/Chroma + embedding 方案）
- **复杂度**：medium 无额外；platform 额外考虑多租户、权限、计费、插件、API 版本管理、数据隔离

### 产品形态推断优先级

CLI > 小程序 > 移动端 > 库 > 桌面 > 后端 > Web（默认）；部署云/本地；识别信号：`cli` / `wechat-miniprogram` / `mobile|flutter|react-native` / `library|sdk` / `desktop|electron|tauri` / `api|backend|server` / `cloud`。

### 平台规范（platformSpec）承载内容示例

- **Web**：语义化 HTML/SEO、响应式、交互反馈（hover/加载/空态/错误）、表单验证、ErrorBoundary、可访问性
- **CLI**：--help 规范、stderr/stdout 分离、退出码、--version、管道兼容
- **后端**：RESTful、统一响应、输入校验、try-catch 全覆盖、幂等、分页、限流
- **小程序**：生命周期、组件通信（properties/triggerEvent）、rpx、审核规范
- **AI 集成**：Key 不进 git、超时重试、兜底展示、成本缓存

这些 platformSpec 持久化在项目配置文件（路径与缺失降级见 02 文件「资源位置约定」），会话创建时注入「项目类型规范」动态段（见 01 文件）。

## 八、原型 Gate（G3/G4）

- **委派前需求确认**：主 Agent 委派设计师 Agent 前必须复述需求理解等用户说「开始」，避免做偏白做一轮。
- **产出即止**：设计师 Agent 只产出 prototype/index.html，不预览、不询问反馈（预览与反馈循环归 主会话）。
- **渲染自查**：主 Agent 收原型后从代码推理做渲染正确性审查（自查清单见 02 文件），不用 Playwright——审查目的是代码级缺陷，模型不一定识图。
- **原型迭代**：prototype/index.html 的修改由主 Agent 直接改（设计迭代不是工程实现），不委派 Builder。

## 九、初始化触发词

- 项目初始化信号：`[系统消息] 项目已创建完毕。项目场景：<label> 项目路径：<path> 关键约束：<dims> 流程提示：先判复杂度，有 UI 且中等及以上就问是否先出原型`
- 直接创建信号：`[系统消息] 用户选择直接创建项目，跳过表单。请按内置流程引导用户。项目名：<name> 已采集：<ctx 或无>`
- 确认开发（CONFIRM_DEVELOPMENT_PROMPT）：`开始执行 task.json 中的开发任务。按顺序逐条推进，每完成一个用 Builder 实现、Evaluator 验收（任务状态由委派执行结果自动回写，无需手动标记），并更新 docs/开发记录.md。全程自动推进不等确认，直到全部完成或用户打断。遇到阻塞写入 escalation.json 并通知用户。遵循项目 TDD 设定。`

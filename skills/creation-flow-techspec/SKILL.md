# 技术方案 + 环境就绪 + 落盘

你（主 Agent）在创建项目引导的最后一步，定技术方案、确认环境就绪、落盘任务。

## 技术方案（G5）

- 实时检索热门方案 + 验证能力边界 + 成本确认（三重验证）
- 2-3 候选方案可对比，但必须给明确推荐
- 主 Agent 代选 + 人话理由；用户确认的是"方案符合目标和预算"

## 环境就绪（G5 后、落盘前必经）

技术方案确认后、落盘 task.json 前，先确认开发环境可构建——让不懂技术的用户不用操心环境配置，环境问题在开发前暴露而非中途。

- **按技术栈执行依赖安装 + 构建验证**（你是架构师，技术栈是你定的，天然知道怎么装依赖）：

| 技术栈 | 依赖安装 | 构建验证 |
|--------|---------|---------|
| Node.js（React/Vue/Electron） | npm install 或 pnpm install | npm run build |
| Python（FastAPI/Django） | pip install -r requirements.txt | python -m compileall |
| Java（Maven） | mvn dependency:go-offline | mvn compile |
| Java（Gradle）/ Android | ./gradlew assembleDebug | ./gradlew compileDebugJavaWithJavac |
| Flutter | flutter pub get | flutter build |
| iOS | pod install | xcodebuild build |
| Go | go mod tidy | go build |
| 静态 HTML | 无依赖 | 直接用浏览器打开 index.html |

- 技术栈不在表内的，按常识判断对应包管理器与构建命令
- **安装/构建失败不卡死流程**：记录具体问题（网络/权限/平台差异）→ 告知用户 → 让用户决定重试 / 跳过 / 手动处理——不静默跳过，也不无限重试

## 落盘 + 进入开发（G6）

- 确认后落 task.json（首任务 = 按已确认原型实现 UI）
- 环境就绪通过后调 开发确认 让用户确认开发（就绪标准③ = 依赖已安装、环境可构建）
- 之后走 Builder/Evaluator 循环（由主 Agent 调度，不用固定流水线限死）

## 🔴 CHECKPOINT · 技术方案与开发确认

1. **技术方案确认**：给出 2-3 候选方案对比 + 明确推荐后，必须等用户确认「方案符合目标和预算」，不能自行落盘
2. **环境就绪确认**：依赖安装 + 构建验证通过后，必须等用户确认开始开发，不能自行进入 Builder/Evaluator 循环
3. **环境失败时**：安装/构建失败时必须告知用户具体问题，让用户决定重试/跳过/手动处理，不能静默跳过

## 失败模式与恢复

| 场景 | 触发条件 | 恢复动作 |
|---|---|---|
| 依赖安装失败 | 网络问题/权限问题/平台不兼容 | 记录具体错误 → 告知用户 → 让用户决定重试/换源/跳过/手动处理，不无限重试 |
| 构建验证失败 | 代码模板有问题/依赖版本冲突 | 修复构建问题后重新验证；连续 3 次失败 → 告知用户具体卡点，让用户决定换技术方案 |
| 技术栈不在表内 | 项目用了冷门技术栈 | 按常识判断包管理器与构建命令，标注「需验证」，执行后确认结果 |
| 用户不确认技术方案 | 给出方案后用户不回复 | 给出推荐默认方案并标注「按推荐方案推进，可随时调整」，不卡住流程 |

## 反例黑名单（不要做以下事情）

- **不要只给一个技术方案**：必须给 2-3 候选方案对比，但必须有明确推荐——不做开放式「你想用什么技术？」
- **不要跳过环境就绪验证**：技术方案确认后必须执行依赖安装 + 构建验证，不能直接落盘 task.json 进入开发
- **不要静默跳过构建失败**：安装/构建失败必须告知用户具体问题，不能假装成功继续
- **不要在技术方案阶段讨论功能**：技术方案只定「用什么技术/怎么架构」，不重新讨论功能范围——功能已在功能共创阶段锁定
- **不要把环境问题丢给用户**：能自动修复的依赖问题先自动修复，实在解决不了才告知用户——不把「npm install 失败」直接丢给用户
